# AI 功能落地 Playbook

把"一个产品怎么开始接入 AI"拆成 9 步。每一步都配《假装懂 AI》的真实做法和踩过的坑，可以直接当面试素材。

一句话方法论：**先定输出契约，再设计输入，然后用工程手段把模型的不确定性关在盒子里，最后才算成本和延迟。**

## 第 1 步：先判断该不该用 AI

规则能解决的就别上模型。判断标准是输入是否非结构化、规则是否写不出来、失败代价是否可接受。

- 本项目：资讯摘要和"产品视角"解读是非结构化文本任务，用 AI
- 反面例子：去重、排序、选取、定时判断全是确定性规则，用代码实现，不消耗 token

## 第 2 步：把任务切到最小

不要让模型"顺便做很多事"。一个模型调用只做一件事，其他都放在模型外面。

- 本项目：每条内容只做一件事——把一条资讯变成一张结构化卡片
- 抓取、去重、排序、并发调度、落盘全部在模型之外

## 第 3 步：先定义输出契约（最关键）

先定 JSON schema，再写 prompt。契约稳定了，前端、管线、模型都可以各自替换。

本项目的契约：

```ts
{
  title: string;        // 中文标题
  summary: string;      // 80-120 字概述
  what: string;         // 这是什么
  highlights: string;   // 核心亮点与实现思路
  productView: string;  // 产品视角
  readTime: string;     // 「X 分钟」
}
```

## 第 4 步：设计输入

给什么、给多少，直接决定成本与效果。给太多烧钱且引入噪声，给太少模型只能编。

- 本项目给：来源、分类、标题、链接、原文内容（截断 2500 字符）

## 第 5 步：写 prompt

四件套：角色、任务、格式、约束。

- 角色：AI 产品经理的情报编辑
- 任务：整理成可直接用于面试准备的结构化卡片
- 格式：只输出 JSON，不要解释文字
- 约束：全中文、字段字数区间、专有名词保留原文、开源项目保留 owner/repo

## 第 6 步：调用层的工程保护

这一步决定能不能上线。四样必备：**总超时、重试、并发、结构化输出模式**。

踩过的坑：最初只设了 socket 空闲超时，没有总超时，DeepSeek 高峰期单次调用挂了 45 分钟；重试 2 次，一条内容就是 45 分钟。加上 60 秒总超时、`response_format: json_object`、重试降到 1 次并加退避、3 路并发之后，8 条内容从 2 小时 15 分压到 **12 秒**。

## 第 7 步：校验与失败处理

两道校验：schema 校验（字段齐全）与业务校验（中文、字数）。不通过就重试。

重试仍失败怎么办，这是产品决策：

- 最初的方案是降级成"标题 + 原文摘要"，结果页面出现英文标题和废话
- 改成**直接跳过这条、换下一条候选**：宁可换内容，也不发布坏内容
- 这是"完整性优先"还是"可用性优先"的取舍，面试里很值得展开讲

## 第 8 步：算成本和延迟

每天多少条、每条多少 token、单次多少钱、延迟目标是多少。

- 本项目：每天 8 条、输入截断 2500 字符、结果可缓存，一天成本在几毛钱以内

## 第 9 步：评估、上线与监控

先人工抽查前几天的产出，再开定时任务，上线后靠日志观察失败率。

两个非模型层面的坑，同样值得讲：

1. 内容没去重，导致连续几天重复推送 → 增加已发布索引，只推新内容
2. 定时判断只看日期，凌晨 3 点就生成，早上 8 点反而跳过 → 加时区时间门控，并改成每小时补偿

## 面试话术

> 我的顺序是：先定输出契约，再设计输入，然后用工程手段把模型的不确定性关在盒子里——超时、重试、结构化输出、schema 校验、失败换候选而不是降级发布。最后才算成本和延迟。模型选型反而是最后一步，因为接口做成 OpenAI 兼容之后，换模型只是改一个环境变量。

## 上线前检查清单

- [ ] 输出契约已定义，且有 schema 校验
- [ ] 单次调用有总超时（不是只有空闲超时）
- [ ] 有重试策略与退避，且重试次数有上限
- [ ] 有并发控制，整体耗时在预算内
- [ ] 失败路径明确：跳过、降级还是重试
- [ ] 成本和每日调用量有上限
- [ ] 密钥只存在环境变量或 Secret，不进仓库
- [ ] 有日志能看到每次失败的原因
- [ ] 人工抽查过至少三天的真实产出
